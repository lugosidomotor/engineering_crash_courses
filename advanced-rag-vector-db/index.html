Intro

Production RAG: a naive RAG-on túl OpenAI Python

Az AI Engineering kurzusban megépítettünk egy alap RAG chatbotot ChromaDB-vel és OpenAI-jal, néhány tucat dokumentumon. Ez kiválóan működik demo-ban és kis prototípusokban, de amikor egy ügyfél megjelenik 50 000 termékkel, 5 000 PDF dokumentummal, 200 párhuzamos felhasználóval és multi-tenant elvárással, a "naive RAG" pipeline elkezd recsegni-ropogni: a latency 3-5 másodperc fölé kúszik, a recall ingadozik, a memory blow-up megöli a workert, és a felhasználói visszajelzések egyre több hallucinált választ jeleznek.

A production RAG ettől különbözik abban, hogy nem egy retrieve+generate pipeline, hanem egy több rétegű retrieval rendszer: dedikált vektor adatbázis (Pinecone, Weaviate, Qdrant, Milvus), hybrid search (dense + sparse), reranking, query transformation, caching layer, evaluation harness és observability. Ebben a kurzusban a Pinecone serverless platformra fókuszálunk, mert ez a legszélesebb körben használt managed vector DB, de a tanult minták (hybrid, rerank, query transform) átültethetők bármelyik másik rendszerre.

A vezérprojekt végig a WebShop Pro Support Bot egy olyan változata lesz, ami elég nagy ahhoz, hogy az in-process megoldások (Chroma, FAISS) ne legyenek elegendők. 50 000 termékkatalógus-tétel, 5 000 dokumentum (visszaküldés, garancia, FAQ, blog), namespace-enként elszeparált tenantok (pl. külön HU és DE üzlet), 1 millió havi query, p95 < 500 ms latency cél. A gyakorlatban ezeket a számokat fogod tervezni, mérni és optimalizálni a kurzus során.

Section 01

Vector DB tájkép: melyiket válaszd? Chroma

A vektor adatbázisok piacán nincs egyetlen "győztes" — különböző use case-ekhez különböző eszközök illenek. A választást három tengely mentén érdemes mérlegelni: scale (mennyi vektor, mennyi query/sec), deployment model (managed SaaS vs self-hosted), és feature set (hybrid search, multi-tenant, filtering, GPU). A WebShop Pro use case-ben (50 000 termék + 5 000 dokumentum + multi-tenant) a Pinecone serverless egy kényelmes default, de például egy strict on-prem GDPR környezetben Qdrant vagy Weaviate self-hosted lenne a választás.

A managed SaaS oldalon a Pinecone a piacvezető: serverless billing modellel (write/read units + storage), erős multi-tenant támogatással (namespace-ek), és agresszíven egyszerű API-val. A Weaviate Cloud Service hasonló kategória, viszont built-in hybrid search BM25 + vector kombinációval. Az AWS OpenSearch szintén kínál vector engine-t, és ha már AWS-en vagy, kényelmes integráció. A self-hosted oldalon a Qdrant (Rust, gyors) és a Milvus (Apache, distributed, GPU support) a két legnagyobb név, illetve a Postgres-be ültethető pgvector extension lett az utóbbi években a "default boring choice" minden Postgres-alapú stacknek.

Az in-process kategóriát nem szabad lebecsülni: a ChromaDB és a FAISS adatkincset jelentenek, ha a use case kicsi (< 100 000 vektor), egyetlen process keretein belül fut, és nincs multi-tenant elvárás. Például egy Streamlit demo, egy notebook prototípus vagy egy egyszemélyes belső tool számára a ChromaDB egyszerűbb és olcsóbb, mint egy Pinecone account. Ahogy nő a méret és bonyolódik a deployment, válaszd a megfelelő managed vagy self-hosted opciót — soha ne erőltesd egyik kategóriát se a másik helyén.

Section 02

Pinecone setup: account, index, kliens Python

A Pinecone-ban dolgozni két lépésben kezdődik: account setup (app.pinecone.io, free tier ad neked egy serverless indexet és pár ezer write/read unitot) és API key generálás (Settings → API keys). Az API kulcsot soha ne commitold gitre — tárold .env fájlban vagy a CI/CD secret-ekben (GitHub Actions secret, AWS Secrets Manager, Azure Key Vault). A free tier elegendő ehhez a kurzushoz, de production esetén a Standard plan $0/hó-tól indul használat-alapú számlázással.

A Pinecone két index típust kínál: serverless és pod-based. A serverless a default új projektekhez — automatikusan skálázódik, csak a tárolás és a query-k után fizetsz, nincs előre lekötött kapacitás. A pod-based a régebbi modell, ahol előre megveszel egy "pod"-ot (p1.x1, s1.x1) fix kapacitással és előre fizetsz havonta. WebShop Pro-hoz serverless-t használunk, mert változó terhelésű (peak órákban 100 RPS, éjjel 1 RPS). A region választás (us-east-1, eu-west-1) fontos: legyen ott, ahol a legtöbb felhasználód van, és ahol a többi service-ed fut, hogy a latency minimális legyen.

A Python kliens telepítése: pip install pinecone>=5.0. Fontos: a 2024-es nagy refactor után a csomag neve pinecone (régen pinecone-client volt), és az API teljesen átalakult. A példáinkban végig a v5+ szintaxist használjuk: from pinecone import Pinecone, ServerlessSpec, majd pc = Pinecone(api_key=...) instanciálja a klienst, és minden további művelet (pc.create_index, pc.Index) ezen keresztül megy.

Section 03

Embedding stratégia: melyik modell, milyen dimenzió? OpenAI

A retrieval minőségét az embedding modell minősége szabja meg — ha rossz embedding-et használsz, hiába van egy csodás Pinecone setup-od, a top-k találatok irrelevánsak lesznek. A 2024-25 körül az iparág defaultja az OpenAI text-embedding-3-small (1536 dim, $0.02/1M token) volt egyszerűsége és ár-érték aránya miatt, de ha angol nyelvű, hosszú dokumentumokon kell maximális minőség, a text-embedding-3-large (3072 dim, $0.13/1M token) érzékelhetően jobb. Mindkettő támogatja a Matryoshka stílusú dimenzió-csökkentést a dimensions paraméteren keresztül — ez azt jelenti, hogy egy 3072-es vektort le tudsz csonkítani 1024-re, és csak ~3-5% recall-t veszítesz.

Magyar és más nem-angol nyelvű dokumentumokra a multilingual modellek javasoltak. A Cohere embed-multilingual-v3.0 (1024 dim) az ipari standard managed multilingual embeddinghez, és kifejezetten erős kelet-európai nyelveken. Self-hosted alternatíva a BGE-M3 (BAAI/bge-m3, 1024 dim, multilingual + multi-functional dense+sparse+colbert egyszerre), és az E5-multilingual-large (1024 dim). Sentence-transformers könyvtárral pár sorban betöltheted ezeket lokálisan, és nincs API költség — viszont GPU kell az ipari sebességhez.

A WebShop Pro esetében a termékleírások és FAQ-k magyar nyelvűek, ezért két lehetőség van: (1) text-embedding-3-small 1536 dim, mert az OpenAI 3-as embedding család elég jó multilingual benchmarkokon és nagy ökoszisztémája van, vagy (2) Cohere embed-multilingual-v3.0, ami minőségében jobb magyaron. A kurzusban az egyszerűség és az AI Engineering kurzussal való folytonosság miatt az OpenAI 3-small-t használjuk 1536-os dimenzióval, ami kompatibilis a Pinecone index dimension=1536 beállításával.

Section 04

Pinecone upsert + query: első end-to-end Python

A Pinecone alapfolyamata egyszerű: upsert (vektor + metaadat beírása vagy felülírása), query (top-k hasonló vektor visszakérése), delete (törlés id vagy filter alapján), és fetch (egy konkrét id lekérése). Az "upsert" az "update or insert" rövidítése — ha az adott id már létezik, felülírja, ha nem, beírja. Nincs külön "create" parancs, ami a development workflow-t leegyszerűsíti.

Az upsert batch limit alapesetben 1000 vektor egy hívásban, de a hivatalos guideline a 100-as batch méret a hálózati overhead és a memóriahasználat optimumáért. Ha 50 000 termékvektort töltesz be, akkor 500 batch HTTP hívást jelent, ami ~30-60 másodperc szekvenciálisan. Async vagy thread pool segítségével párhuzamosítható: 8 worker-rel ~5-8 másodperc alá viheted.

A query mindig egy vektorral indul (a kérdés embeddingje), és visszaadja a top_k legközelebbi vektor idejét, score-ját, és opcionálisan a metaadatát. A három fontos paraméter: top_k (általában 5-20, RAG-ban tipikusan 5 a végső, de retrieval+rerank pipeline-ban 50-100 előretrievelünk), namespace (a multi-tenant izoláció kulcsa, lásd S11), és filter (metadata-alapú hard szűrő, pl. {"category": {"$eq": "laptop"}}). A filter a query előtt fut, így gyors és olcsó — használd ki, ha tudod a kategóriát vagy más metaadatot.

# Upsert: 3 termékvektor metaadatokkal
def embed_texts(texts):
    resp = client.embeddings.create(
        model="text-embedding-3-small",
        input=texts, dimensions=1536,
    )
    return [d.embedding for d in resp.data]

products = [
    {"id": "prod-1001", "text": "Lenovo ThinkPad X1, 16GB RAM, 1TB SSD",
     "meta": {"category": "laptop", "price": 899000, "brand": "Lenovo"}},
    {"id": "prod-1002", "text": "Apple MacBook Air M3, 16GB RAM, 512GB SSD",

Section 05

Chunking stratégiák haladóknak LangChain

A chunking az a lépés, amelyben a hosszú dokumentumokat (PDF, HTML, Markdown, plain text) annyira kis darabokra szabdaljuk, hogy egyetlen chunk beleférjen az embedding modell kontextusába (8 192 token a 3-small esetén) és értelmes egységet képezzen a retrieval szempontjából. Egy túl nagy chunk "felhígítja" az embeddinget — ha egy 2 000 szavas chunkban csak egy mondat releváns a kérdésre, a vektor maga csak gyengén lesz hasonló a query embeddingéhez. Egy túl kicsi chunk viszont elveszti a kontextust — ha egy mondatot embeddelsz névmással ("ez a termék"), nem lehet tudni, mire utal.

A fixed-size chunking a legegyszerűbb: minden N karakter (tipikusan 500-1500), N*0.1-N*0.2 átfedéssel (overlap, hogy a határos információk ne vesszenek el). Ez gyors, deterministic, de "vakon" vág — egy mondat vagy bekezdés közepén is. A recursive chunking (LangChain RecursiveCharacterTextSplitter) okosabb: hierarchikus separator listát próbál (["\n\n", "\n", ". ", " "]), és először a "soft" határokon vág. Ez a default ipari recept, és általában jó eredményt ad ~10 perc alatt beállítva.

A semantic chunking még tovább megy: minden mondatot embedeli, majd ott vág, ahol az egymás utáni embeddingek közötti hasonlóság hirtelen leesik (azaz a téma vált). Ez szebben tagol bonyolult dokumentumokat (pl. egy hosszú jogi szöveg), de drágább (extra embedding hívások) és lassabb. A document-aware chunking a strukturális metaadatot használja: Markdown header-ek alapján bont (LangChain MarkdownHeaderTextSplitter), HTML <section>-ök, vagy PDF heading-ek mentén. Az agentic chunking az új generáció: egy LLM-et kérünk meg, hogy szakértő módon tagolja a dokumentumot ("bontsd fel ezt logikai részekre, mindegyikhez adj egy summary-t"). Drága, de a minősége legjobb.

chunks_md = md_splitter.split_text(doc)

print(f"Recursive: {len(chunks_recursive)} chunks")
for i, c in enumerate(chunks_recursive):
    print(f"  [{i}] {c[:60]}...")

print(f"\nMarkdown: {len(chunks_md)} chunks")
for c in chunks_md:
    print(f"  meta={c.metadata} content={c.page_content[:50]}...")

Section 06

Hybrid search: dense + sparse együtt Python

A pure dense vector search (csak embedding-alapú) elképesztően jó szemantikus értésben, de van egy gyengéje: a ritka, specifikus termék-kódok, SKU-k, számozott azonosítók esetén megakad. Ha valaki rákeres a "P-3344-A" kódra, a dense embedding nem fog rátalálni a "P-3344-A SSD modul Lenovo laptop" termékre, mert a vektor-tér nem tartja számon a karakter szintű egyezést. Ezt a problémát oldja meg a hybrid search: kombináljuk a dense semantic search-öt egy sparse lexical search-csel (BM25 vagy SPLADE).

A BM25 (Best Matching 25) a klasszikus IR algoritmus: term frequency × inverse document frequency, hossz-normalizálással. Egy lexikai mátrix-szal dolgozik, ahol a sorok dokumentumok, az oszlopok szavak, és minden cella a szó relevanciáját mutatja a dokumentumban. A BM25 erős a pontos szóegyezésnél (SKU, jogi kifejezés, márkanév), de gyenge a szemantikai szinonimáknál ("autó" vs "kocsi"). A dense embedding pont fordítva: jó szinonimáknál, gyenge ritka tokeneknél. A kettő kombinációja a sweet spot.

A Pinecone natív hybrid index-szel támogatja ezt: az indexet metric="dotproduct"-tal hozod létre, és minden vektorhoz fűzhetsz egy sparse_values mezőt is. A query során is elküldesz mind dense, mind sparse vektort, és Pinecone a "convex combination" alapján rangsorol: score = α × dense + (1−α) × sparse. Az α (alpha) tipikusan 0.5-0.7 a dense felé tolva. Alternatíva a Reciprocal Rank Fusion (RRF): külön futtatsz egy dense és egy BM25 keresést, majd a két ranking listát kombinálod a 1/(k+rank) formulával.

# Hybrid query: dense + sparse alpha=0.6
def hybrid_score(dense, sparse, alpha=0.6):
    return {
        "values": [v * alpha for v in dense],
        "sparse_values": {
            "indices": sparse["indices"],
            "values": [v * (1 - alpha) for v in sparse["values"]],
        },
    }

scaled = hybrid_score(dense_vec, sparse_vec, alpha=0.6)

results = index.query(
    vector=scaled["values"],
    sparse_vector=scaled["sparse_values"],
    top_k=5,
    namespace="hu-products",
    include_metadata=True,
)

    print(f"id={m.id}  hybrid_score={m.score:.4f}  text={m.metadata['text']}")

Section 07

Reranking: top-50 → top-5 minőségi szűrés Python

A reranking egy második menet a retrieval pipeline-ban: a vector DB visszaad pl. top-50 jelöltet, ezeket egy cross-encoder modell pontosan átskálázza, és csak a legjobb 5-öt adjuk át az LLM-nek a kontextusba. A logika: a vector search egy "first-pass" gyors szűrő (cosine similarity 1536 dim-en, ami jó, de zajos), míg a cross-encoder egy "second-pass" lassú-de-pontos osztályozó, ami a query+document párt egyszerre nézi és egy 0-1 közötti relevancia score-t ad.

A különbség kritikus: a bi-encoder (a vector search-ben használt embedding modell) külön-külön embedeli a query-t és a dokumentumot, majd vektor-hasonlóságot számol — ez gyors (előre embedeled mindent), de elveszti a finom interakciót. A cross-encoder (reranker) a query-t és a dokumentumot egyszerre adja át a transformer modellnek (egy hosszú prompt formájában), így a self-attention rétegek látják a kapcsolatokat. Lassabb (futás-időben kell minden query-document párra hívni), de pontosabb. Tipikusan 5-10× recall@5 javulás.

A piacvezető rerankerek: Cohere rerank-v3.0 (managed API, $2/1k search, multilingual, kiváló minőség), BGE-reranker-v2-m3 (open-source, BAAI, multilingual, self-hosted), Jina Reranker v2 (managed, gyors, multilingual). A WebShop Pro esetében a Cohere rerankert használjuk a managed kényelemért és a multilingual minőségért. A pipeline: Pinecone top_k=50 → Cohere rerank → top_k=5 → LLM. A latency overhead ~100-200 ms, ami sokat hoz a recall-ban.

Section 08

Multi-vector retrieval: parent-child + ColBERT Chroma

A multi-vector retrieval azt jelenti, hogy egy logikai dokumentumhoz több embedding tartozik, és a retrieval ezekből összevontan keres. Két fő pattern van: a parent-child minta és a late interaction (ColBERT) minta. Mindkettő ugyanazt a problémát oldja meg: ha egy nagy dokumentumhoz egyetlen embedding tartozik, a vektor "összemossa" az összes témát; ha viszont sok kis chunkra bontod, elvész a kontextus a generálásnál.

A parent-child minta: a dokumentumot kis chunkokra bontod (mondat- vagy bekezdésszintű), és ezekre embeddinget gyártasz. Viszont az indexben minden chunkhoz megőrzöd a parent_id-t (a teljes dokumentum vagy nagyobb szekció id-ja). A retrieval során a chunk-szintű vektorokon keresel (jó precízió), majd a top találatok parent_id-ja alapján visszanyered a teljes dokumentumot, és AZT adod át kontextusként az LLM-nek (jó recall, jó kontextus). A LangChain ParentDocumentRetriever ezt a mintát implementálja.

A ColBERT (Contextualized Late Interaction over BERT) egy másik megközelítés: minden dokumentumhoz nem egy 1536-dimenziós vektor tartozik, hanem token-szintű vektorok mátrixa (pl. egy 100 szavas dokumentumhoz 100 × 128 dim mátrix). A query-ből is token-szintű vektorokat kapunk, és a "late interaction" így zajlik: minden query token a legközelebbi dokumentum tokent találja meg, és ezek átlagát vesszük. Ez sokkal pontosabb, mint a single-vector cosine, de drasztikusan több storage-ot igényel. Pinecone még nem támogatja natívan, de a Vespa, Qdrant (multi-vector mode), és a RAGatouille open-source library igen.

# Parent-child minta Pinecone-on: chunk-szintű embedding, parent_id metaadatban

Section 09

Query transformation: HyDE, expansion, decomposition OpenAI

A felhasználói kérdések ritkán optimálisak retrieval szempontból. Egy kérdés ("Tudtok ide szállítani holnap reggelre?") rövid, kontextus-szegény, és a vector embedding-je nem feltétlenül passzol a tudásbázisbeli "Sürgős kiszállítás 24 órán belül országosan, 4 990 Ft" mondat embedding-jéhez. A query transformation egy LLM-alapú előfeldolgozási lépés, amely a query-t egy retrieval-barát formára hozza. Négy fő technika létezik.

A HyDE (Hypothetical Document Embeddings): az LLM-et megkérjük, hogy generáljon egy hipotetikus választ a kérdésre, AZT embeddeljük, és AZ embeddinggel keresünk. A logika: a tudásbázisban lévő dokumentumok stílusa és vokabulárja közelebb áll egy "válasz" stílusához, mint egy "kérdés" stílusához, így a hipotetikus válasz embeddingje jobban lesi a megfelelő dokumentumokat. A query expansion: az LLM-et megkérjük, hogy generáljon 3-5 alternatív megfogalmazást ugyanarra a kérdésre, mindegyikkel külön keresünk, és a top találatokat egyesítjük (RRF-fel vagy egyszerű union-nal).

A step-back prompting: az LLM-et megkérjük, hogy egy "magasabb absztrakciós szintű" verziót adjon a kérdésnek ("Mi a kiszállítás szabályai?" helyett "Milyen kiszállítási opciók vannak?"). Ezt használjuk retrieval-re, és a top dokumentumokból válaszolunk az eredeti kérdésre. A query decomposition: a komplex kérdést részkérdésekre bontjuk ("Tudtok holnap reggelre szállítani Debrecenbe és mennyibe kerül?" → "Mikor érkezik holnapi rendelés Debrecenbe?" + "Mennyibe kerül az expressz kiszállítás?"), külön-külön retrieve-elünk, és az eredményeket konkatenáljuk.

# HyDE: hipotetikus dokumentum generálás, AZT embedeljük
def hyde_search(question, top_k=5):
    # 1) LLM generál egy hipotetikus választ
    hyp_resp = client.chat.completions.create(
        model="gpt-4o-mini",

            {"role": "system", "content": "Adj egy rövid, faktuális választ webshop témában. Ne írd, hogy nem tudod -- találgass plauzibilisen."},
            {"role": "user", "content": question},

    )
    return hypothetical_doc, results.matches

Section 10

Metadata filtering: operátorok és index-design Python

A Pinecone metadata filtering a vector search egyik legértékesebb képessége: a filter paraméter előbb fut, mint a vektor-keresés, így gyors és olcsó. Ha tudod, hogy "csak laptop kategóriát szeretnék" vagy "csak az utolsó 30 nap dokumentumait", akkor egy hard filterrel a kereső tér lecsökken, a query latency javul, és a retrieved eredmények pontosabbak. Helytelen filter-design viszont sokat ronthat: ha minden vektorhoz 50 metaadat mező van, és mindegyikre filterezel, a Pinecone backend lassul.

A támogatott operátorok: $eq (equal), $ne (not equal), $in (egyik a listában), $nin (egyik sem), $gt, $gte, $lt, $lte (numerikus összehasonlítás), $exists (mező létezik vagy sem). Logikai kombinálás: $and, $or. Beágyazható: {"$or": [{"category": {"$eq": "laptop"}}, {"$and": [{"price": {"$lte": 100000}}, {"brand": {"$in": ["HP", "Lenovo"]}}]}]}. A Pinecone NEM támogatja a regex-et, az aggregációt (group by), és a join-okat — ha ezek kellenek, akkor secondary store-ral (Postgres) kell kombinálni.

Az index-design szempontok: (1) Pinecone metadata limit 40 KB / vektor, ezért a hosszú szöveget (full document) NE pakold metaadatba — csak az id-t, és a teljes szöveget tárold külső store-ban (Postgres, S3). (2) Csak azokat a mezőket vedd a metaadatba, amelyekre filterezni akarsz vagy visszakapni akarsz a query-ben. (3) High-cardinality mezőkre (pl. user_id milliós választékkal) a namespace jobb választás, mint a metadata filter (lásd S11). (4) A timestamp-ot Unix epoch-ban (integer) tárold, ne ISO stringben — gyorsabb a numerikus filter.

Section 11

Namespace és multi-tenant izoláció Python

A Pinecone namespace egy logikai partíció egyetlen indexen belül. Minden upsert és query egy konkrét namespace-be megy (vagy ha nem adsz meg, az alapértelmezett "" üres namespace-be). A namespace-ek között teljes az izoláció: egy customer-A namespace query-je SOHA nem kap találatot a customer-B namespace vektoraiból. Ez egy szerver-oldali garancia, nem csak konvenció — ezért használhatod multi-tenant biztonsági modellként.

A multi-tenant SaaS RAG-szolgáltatás (pl. egy customer support bot, amit több ügyfél-cég használ) tipikus mintája: egy index, sok namespace. Minden tenant (ügyfél) saját namespace-t kap (pl. tenant-acmecorp, tenant-globaltech), és az alkalmazás-réteg gondoskodik arról, hogy a query mindig csak a jó tenant namespace-ét hívja. Ez egyszerűbb deployment (egy index admin szempontjából), kisebb költség (közös storage és compute), és tiszta izoláció (nem keveredhet a vektor a tenantok között).

A namespace-ek nem korlátlanok: a Pinecone serverless plan-en a 10 000 namespace / index egy tipikus limit, ami a legtöbb SaaS use case-hez bőven elég. Performance-ban a namespace-eknek csekély overhead-jük van (külön Bloom filter-rel és index-szegmenssel dolgoznak), de ha 100 000+ tenanttal van dolgod, érdemes tenant-shardingot használni: tenanto-kat csoportosítasz közös namespace-be, és a query-ben metadata filterrel ({"tenant_id": {"$eq": "..."}}) szűröd. Ez a "namespace per tenant" vs "metadata-filter per tenant" trade-off egy klasszikus multi-tenant database tervezési kérdés.

Agentic RAG: az LLM dönt, mikor kell retrieve OpenAI LangChain

A naive RAG minden query-re lefuttat egy retrieval-t, akár van rá szükség, akár nincs. Ha a felhasználó azt mondja "Köszi, ez nagyon segített!", a rendszer akkor is fog vector search-ölni — fölösleges latency, fölösleges költség, fölösleges zaj a kontextusban. Az agentic RAG abban különbözik, hogy az LLM-et hagyjuk eldönteni: kell-e most retrieve-elni, és ha igen, MILYEN paraméterekkel. Ezt OpenAI tool calling-gal valósítjuk meg, amelyet az AI Engineering kurzusban már láttál.

A pattern: regisztráljunk egy retrieve_documents tool-t, aminek a paramétere a query string. Az LLM a beszélgetés állapota alapján dönti el, hogy a választáshoz kell-e információt keresni. Ha igen, kibocsát egy tool_calls-t, mi azt elvégezzük (Pinecone query), visszaadjuk az eredményt mint tool role message, és az LLM ezzel válaszol. Ha az LLM úgy ítéli, hogy nem kell retrieve, csak válaszol egyenesen. Ez a "decide-and-retrieve" minta intelligensebbé teszi a chatbotot, és csökkenti a fölösleges költséget.

Az iteratív agentic RAG még tovább megy: az LLM több retrieve hívást is kibocsáthat egymás után. Például: "Milyen laptopot ajánlsz egy programozónak 500 000 Ft alatt, ami fut Linuxon?" → első retrieve "olcsó laptop programozóknak" → másodi retrieve "laptop Linux kompatibilitás" → harmadik retrieve "laptop ár 500000 alatt" → válasz. Ez a multi-step retrieval, és a LangGraph vagy CrewAI keretrendszerek erre építenek state machine-eket. A kompromisszum: drága (sok LLM hívás + sok Pinecone query), lassú (több round-trip), de a komplex kérdéseken sokkal jobb minőség.

Evaluation: recall@k, latency, A/B teszt Python

A production RAG egyik leggyakoribb hibája, hogy a fejlesztő érzésre dönt: "ez most jól néz ki, deployolom". Pár hét múlva kiderül, hogy a felhasználók fele rossz választ kap, mert a retrieval recall@5 csak 0.6 — vagyis a queries 40%-ánál a helyes dokumentum nincs benne a top 5-ben. Az evaluation egy folyamatos mérési diszciplína, és minden architektúra-változtatás (új embedding modell, új reranker, új chunking) előtt és után meg kell mérni.

A retrieval-szintű metrikák: recall@k = (a top-k-ban lévő releváns dokumentumok száma) / (összes releváns), precision@k = (top-k-ban lévő releváns dokumentumok) / k, MRR (Mean Reciprocal Rank) = a helyes dokumentum első találati pozíciójának reciproka. Ezekhez kell egy ground truth dataset: 50-200 query, mindegyikhez kézzel jegyzett "ez a helyes dokumentum-id" annotáció. A WebShop Pro esetében ezt a customer support csapat heti 1-2 órájával lehet összeállítani, ahogy logoljuk a produkciós kérdéseket.

A generation-szintű metrikák: RAGAS context_precision (a retrieved kontextus mennyire releváns), context_recall (a ground truth válasz hány állítása lefedett a kontextusban), faithfulness (a végső válasz mennyire alapszik a kontextuson, nem hallucinált). Ezekhez nem kell ground truth, csak referencia válasz — egy LLM-as-judge méri. Részletesebben a RAG Evaluation & AI Safety kurzusban. A latency-szintű metrikák: p50, p95, p99 a teljes query latency-re, külön-külön az embedding API, Pinecone query, reranker, és LLM hívásokra. SLO példa: p95 < 500 ms a teljes RAG pipeline-on.

import time

def recall_at_k(k=5, namespace="hu-docs"):
    hits, latencies = 0, []
    for item in ground_truth:
        t0 = time.perf_counter()
        qvec = embed_texts([item["query"]])[0]
        res = index.query(vector=qvec, top_k=k, namespace=namespace, include_metadata=False)
        latencies.append((time.perf_counter() - t0) * 1000)
        retrieved_ids = [m.id for m in res.matches]
        if item["correct_id"] in retrieved_ids:
            hits += 1
    recall = hits / len(ground_truth)
    p50 = sorted(latencies)[len(latencies) // 2]
    p95 = sorted(latencies)[int(len(latencies) * 0.95)]
    return recall, p50, p95

Caching layer: embedding és semantic cache Python

A RAG pipeline három pénzbe kerülő komponensből áll: embedding API hívás (~$0.02 / 1M token), Pinecone query (~$0.001 / 1k query), LLM hívás (~$2.50 / 1M output token GPT-4o-val). Egy átlagos chat session 5-10 query, mindegyikhez 1-2 embedding hívás és 1 LLM hívás. 10 000 napi user × 8 query × $0.005 átlagos query költség = $400/nap = $12 000/hó. Ennek 30-50%-át cache layer-rel le tudod faragni, ha okosan csinálod.

Az embedding cache a legegyszerűbb: ha ugyanaz a string érkezik (akár felhasználói query, akár indexelendő dokumentum), nem hívod újra az OpenAI API-t, hanem visszaadod a cachelt vektort. Egy Redis (vagy lokális dict prototípusra) SHA256(text) → vector_blob mapping. Egy átlagos chatben sok query ismétlődik (top 100 query a forgalom 30-50%-át adja), így a hit rate 40-60% lehet. Költség-megtakarítás: ~$0.01 / 1k token, plusz a latency 200-500 ms-ról 1-5 ms-ra esik.

A semantic cache okosabb: nem pontos string-egyezés, hanem szemantikus hasonlóság. Eltároljuk a cachelt query-k embeddingjét, és új query-nél megnézzük, van-e olyan cachelt query, ami > 0.95 cosine similarity-jú. Ha igen, visszaadjuk a cachelt választ — még ha a felhasználó megfogalmazása kicsit más is. Pl. "Mikor érkezik a csomag?" és "Mennyi a kiszállítás ideje?" ugyanazt a választ kapja. Veszélye: false positive (két hasonló, de eltérő kérdés ugyanazt kapja). Threshold-ot körültekintően kell beállítani, és A/B tesztelni. Tooling: GPTCache, LangChain RedisSemanticCache.

# Egyszerű in-memory embedding cache + semantic cache
import hashlib
import numpy as np

embedding_cache = {}     # {sha256(text): vector}
answer_cache = []        # [(query_vector, query_text, answer)]

def embed_with_cache(text):
    key = hashlib.sha256(text.encode()).hexdigest()
    if key in embedding_cache:
        return embedding_cache[key], "hit"
    vec = embed_texts([text])[0]
    embedding_cache[key] = vec
    return vec, "miss"

def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def semantic_lookup(query, threshold=0.95):
    qvec, _ = embed_with_cache(query)
    for cached_vec, cached_q, cached_ans in answer_cache:
        sim = cosine(qvec, cached_vec)
        if sim > threshold:
            return cached_ans, f"hit (sim={sim:.3f}, original='{cached_q}')"
    return None, "miss"

# Pl. egy első query: nincs cache, válaszolunk és mentjük
q1 = "Mikor érkezik a csomag?"
ans1 = "3-5 munkanap a standard kiszállítás."
v1, _ = embed_with_cache(q1)
answer_cache.append((v1, q1, ans1))

# Második, hasonló query: semantic cache hit
q2 = "Mennyi idő alatt jön a kiszállítás?"
ans, status = semantic_lookup(q2)
print(f"q2='{q2}'  cache_status={status}")
print(f"cached answer: {ans}")

Cost & scaling: Pinecone serverless árazás OpenAI

A Pinecone serverless árazás három tételen alapul: storage ($0.33 / GB / hó), write units ($4 / 1M WU; egy upsert vektorára ~1-3 WU), read units ($16 / 1M RU; egy query ~5-15 RU a top_k és metadata mérettől függően). Ezek a 2025-ös listaárak, és van free tier (1 GB storage, 5M WU, 5M RU havonta), ami egy középméretű prototípushoz elegendő. A pod-based modell egy fix havi díj a kapacitásra (p1.x1 ~$70/hó), de a serverless kicsi-közepes use case-eknél jobb.

A WebShop Pro költségszámítás: 50 000 termék × 1536 dim × 4 byte = ~300 MB nyers vektor, plusz 50 000 chunk × 5 KB metadata = 250 MB metadata. Összesen ~550 MB tárolás → ~$0.18 / hó. Egyszeri upsert 50 000 vektorra ~150 000 WU = $0.60. Napi 10 000 query × 30 nap = 300 000 query/hó × 10 RU = 3M RU = $48 / hó. Embedding API hívások (300 000 query × ~50 token avg = 15M token) × $0.02/1M = $0.30. Összesen Pinecone + embedding: ~$50 / hó. Ehhez jön az LLM költség (lásd alább).

A self-hosted alternatíva breakeven point: ha a havi Pinecone számla > $300-500, érdemes számolni az ön-hostolt Qdrant-tal vagy Weaviate-tel. Egy közepes Hetzner CCX23 instance (~$30/hó, 16 GB RAM, 4 vCPU) elbír 5-10 millió vektort, és a TCO (Total Cost of Ownership) belefér havi $100-150-be DevOps idővel együtt. Cserébe veszítesz a managed kényelemből, és vállalod a backup, monitoring, scaling ops-t. A döntést mindig a teljes cost-of-ownership alapján kell meghozni, nem csak a license-fee alapján.

Production deployment: FastAPI + Pinecone + cache FastAPI Python

A production RAG endpoint egy HTTP service, amit a frontend hív. A WebShop Pro architektúrája: a felhasználó beír egy kérdést a chatbot widget-be → JS POST /api/chat → FastAPI endpoint → cache check → embedding → Pinecone query → reranker → LLM → válasz. A teljes round-trip cél < 1.5 másodperc. A FastAPI ideális választás: async natívan, OpenAPI auto-doc, Pydantic validation, könnyen tesztelhető és deployolható.

Az async fontos: a Pinecone, OpenAI és Cohere API-k mind hálózati hívások, és a synchronous Python esetén a worker blokkol a válaszra várva. async def handler-ben await-tel ezek a hívások konkurensen futnak, és egy uvicorn worker 100+ concurrent request-et tud kiszolgálni. A rate limiting kritikus: az OpenAI és Cohere mind RPM (requests per minute) limittel rendelkezik, túllépéskor 429 jön vissza. Használj slowapi-t vagy egy Redis-alapú rate limit pattern-t a downstream API hívások limitálásához.

A monitoring production-ben elengedhetetlen: minden /api/chat hívás logolja a query-t, latency-t, hit/miss cache statust, retrieved IDs-t, end user feedback-et. Tooling: Prometheus + Grafana a latency p50/p95/p99 dashboardhoz, OpenTelemetry a distributed tracing-hez (request végigkövetése a stack-en), Sentry a hibajelzéshez. A health endpoint (/health) ellenőrzi a Pinecone, OpenAI, Cohere, Redis kapcsolatot — ezt a Kubernetes liveness/readiness probe használja.

from slowapi import Limiter
from slowapi.util import get_remote_address

app = FastAPI(title="WebShop Pro RAG API")

class ChatRequest(BaseModel):
    query: str
    tenant: str = "hu"
    top_k: int = 5

class ChatResponse(BaseModel):
    answer: str
    sources: list[str]
    latency_ms: int
    cached: bool

@app.post("/api/chat", response_model=ChatResponse)
@limiter.limit("30/minute")
async def chat(request: Request, body: ChatRequest):
    t0 = time.perf_counter()
    ns = f"tenant-{body.tenant}"

    # 1) Semantic cache
    cached, _ = semantic_lookup(body.query)
    if cached:
        return ChatResponse(answer=cached, sources=[], cached=True,
                            latency_ms=int((time.perf_counter() - t0) * 1000))

    # 2) Embedding + Pinecone first-pass
    qvec, _ = embed_with_cache(body.query)
    first_pass = index.query(vector=qvec, top_k=50, namespace=ns, include_metadata=True)

    # 3) Cohere rerank
    docs = [m.metadata["text"] for m in first_pass.matches]
    rer = co.rerank(model="rerank-multilingual-v3.0", query=body.query, documents=docs, top_n=body.top_k)
    top_docs = [docs[r.index] for r in rer.results]

    # 4) LLM
    ctx = "\n\n".join(top_docs)
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Válaszolj kizárólag a megadott kontextus alapján."},
            {"role": "user", "content": f"Kontextus:\n{ctx}\n\nKérdés: {body.query}"},
        ],
    )
    answer = resp.choices[0].message.content
    answer_cache.append((qvec, body.query, answer))

    return ChatResponse(answer=answer, sources=top_docs, cached=False,
                        latency_ms=int((time.perf_counter() - t0) * 1000))
